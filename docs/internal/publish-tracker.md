# Per-publication confirm and return tracking

The record for `pika/publish_tracker.py`, which lets an application learn the broker verdict of each individual publish when several publishing threads share one channel, publishes can carry identical bodies, and one confirm frame can cover several publishes.

## Why delivery tags alone do not identify a publication

Publisher confirms address a publish by its delivery tag, obtained from `on_publish`. Two broker signals break tag-only bookkeeping:

- A `Basic.Ack` or `Basic.Nack` with `multiple=True` confirms every outstanding tag up to the frame's tag in one frame, so one frame resolves several publications and the application has to keep the tag-to-publication map itself.
- A `Basic.Return` frame carries no delivery tag at all. Its method fields are reply code, reply text, exchange and routing key; the only thing that links it back to the publish is content the application put in the message. Routing key cannot serve when two publishes use the same one, and the body cannot serve when two publishes are identical, which the motivating workload does on purpose.

The tracker therefore stamps every publish with a unique id in a headers field (`x-pika-message-id` by default) and correlates on two keys: delivery tag for confirms, message id for returns. The header is added to a copy of the caller's properties rather than by mutating the object, because a properties instance shared across publishes would otherwise cross-connect their ids.

## Frame ordering and the outcome state machine

RabbitMQ answers an unroutable mandatory publish with `Basic.Return` and then `Basic.Ack` for the same sequence number; the measurement is in `thread-safe-connection.md`. A publication therefore moves through these outcomes:

- `Pending` until a terminal frame is processed.
- `Returned` when the return arrives. The later ack does not overwrite it; the ack method is still stored on the publication as `confirm_method`, so both pieces of evidence are retained.
- `Acked` or `Nacked` when a confirm covers the tag and no return was seen.
- `Uncertain` when the channel goes away while still pending.

`Returned`, `Acked` and `Nacked` are terminal only for the life of the channel; see the late-frame note below for what a disconnect changes. A nack paired with a return is theoretically possible (the broker can nack after a return under internal failure), and the same rule applies: the return stays the routing verdict and the nack is recorded beside it.

A confirm for a tag no publication is bound to updates only the `last_confirm_tag` boundary. A return whose message id matches nothing, including one missing the header entirely, is retained on the snapshot as `unmatched_returns` with a warning rather than dropped: swallowing it would leave an application unable to account for a frame the broker definitely sent.

## One tracker per channel generation

The broker numbers delivery tags from 1 per channel and resets the counter when a channel is closed and the same channel number is reopened. A tracker that lived across both generations would bind the new channel's tag 1 onto the old channel's tag-1 publication, so every later confirm hit the wrong record. `PublishTracker` is therefore constructed per channel and never reset. Reopening a channel means constructing a new tracker; the old one stays readable and keeps reconciling frames that were already queued on the old channel's worker when it closed.

This is why publication identity is the message id, not the tag. The id is generated by the client and unique within the tracker, so an old tracker accepting a late return and a new tracker accepting a fresh tag-1 publish cannot interfere even though both speak of delivery tag 1.

## What disconnect hands back

A publication with no observed verdict is not evidence of failure; the broker may have confirmed it on a frame still in the socket buffer. `mark_disconnected()` turns every `Pending` publication into `Uncertain` and wakes every waiter, instead of leaving `wait` blocked on a channel that can no longer answer. `snapshot()` then reports the actual known boundary:

- `last_delivery_tag`: the highest tag an `on_publish` reported, i.e. the last publish the client knows the broker numbered.
- `last_confirm_tag`: the highest tag any confirm frame covered. The gap above it is unverified even for publishes whose frames were written.
- `resolved`, `pending` and `uncertain`, each as a tuple of publications.
- `unmatched_returns`.

A frame already in flight when the connection dropped can be dispatched after `mark_disconnected()`. The tracker still matches it: a return moves an `Uncertain` publication to `Returned`, and a confirm records the method. Uncertain means "no verdict observed at the instant of the loss", not "no verdict can ever arrive", so a later observation upgrades it. The application decides whether to trust that late evidence or republish on the new channel.

## Threading

All state sits behind one `threading.Condition`. Three threads touch it: publishing threads register before the publish frame is written and read snapshots; the IOLoop thread runs `on_publish`, which only binds the tag; the channel's worker thread runs `on_confirm` and `on_return`. Registration happens before `basic_publish` is called, so a broker answer cannot arrive ahead of the record it belongs to. A failure inside `basic_publish` removes the registration again, since nothing was written.

`wait` and `wait_all` are condition waits with optional timeouts; they never poll. `wait_for_delivery_tag` covers the gap where a thread-safe `basic_publish` has returned but its IOLoop-thread `on_publish` has not run yet, which the `next_publish_seq_no` measurement in `thread-safe-connection.md` shows is a real race. `mark_disconnected` is what bounds the waits by liveness rather than by a clock, matching the close guarantees in that page.

## Rejected designs

**Correlating returns by body or routing key.** The workload publishes byte-identical bodies deliberately, and several publications can share a routing key. Either key merges distinct publications and attributes the return to the wrong one whenever more than one is outstanding. The header id is the only correlation the protocol leaves the client.

**Sharing one tracker across a reopened channel.** The delivery-tag reset at reopen collides tag 1 of the new generation with tag 1 of the old one. Per-channel construction removes the collision and keeps the old generation's late frames attributable.

**Treating `Basic.Ack` as proof of routing.** The broker acks an unroutable mandatory publish after returning it. Code that closes a publication on the ack alone reports success for a message no queue holds, which is the defect `add_on_return_callback` exists to prevent; the tracker keeps the return primary.

**Dropping unmatched returns.** A return without a tracked id means a frame the broker sent has no home in the bookkeeping. Dropping it hides the discrepancy; retaining it on the snapshot makes an application misconfiguration (a foreign publisher on the channel, a stripped header) observable.

## Known gaps

- The tracker targets `pika.Connection`'s channel, which is the only adapter exposing `on_publish`. `BlockingChannel` has no tag callback and already raises `UnroutableError` synchronously per publish, so it does not need this layer; the other adapters are deprecated for removal in 2.0.
- A publication whose `on_publish` never ran (the publish was scheduled on the IOLoop but the connection died first) stays `Pending` and becomes `Uncertain` with no delivery tag. Its frame may never have reached the broker, so republishing is the caller's decision; the tracker cannot distinguish "not sent" from "sent but unnumbered in the client".
